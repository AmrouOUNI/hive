# Capability Protocol

## What Are Capabilities

Some things agents need — reviewing code, structuring an ADR, running an incident response — are **not hive-specific**. Modern Claude Code environments already ship excellent skills for them (built-in slash commands, plugin skills, or project skills). Hive does not duplicate them.

Instead, agents invoke an abstract **capability** (`capability:{name}`). The client project's `skills-map.json` resolves each capability to whatever implementation exists in that environment. If nothing is mapped, the agent falls back to its own judgment using the fallback guidance below.

```
AGENT.md says:                 skills-map.json resolves:
  "use capability:code-review"   → "/code-review" (built-in)
                                  → "engineering:code-review" (plugin)
                                  → ".claude/skills/my-review" (project skill)
                                  → null (fallback: agent's inline judgment)
```

This is the same ports & adapters idea as `protocols/adapters.md`, applied to skills instead of tools:
- **Adapters** answer "HOW do I reach this project's infrastructure?" (logs, deploys, DB)
- **Capabilities** answer "HOW do I perform this generic practice in this environment?" (review, ADR, incident)

## Capability Registry

| Capability | Purpose | Used by | Common providers (examples) | Fallback if unmapped |
|---|---|---|---|---|
| `code-review` | Review a diff/branch for correctness, security, tests | qa-lead, sr-backend | `/code-review`, `engineering:code-review` plugin | Diff review with a correctness/tests/security checklist; post findings |
| `refactor` | Simplify and clean up code without changing behavior | sr-backend | `/simplify`, `engineering:tech-debt` | Identify duplication and dead code; propose scoped, reviewable cleanups |
| `security-review` | Audit changes or a codebase area for vulnerabilities | sec-chief | `/security-review`, security plugins | OWASP Top 10 pass: injection, auth, secrets, access control, error leakage |
| `architecture-decision` | Write/evaluate an ADR with trade-offs | architect, cto | `engineering:architecture` | Context → options → decision → consequences format; post to the decisions category |
| `design-review` | Review a system/feature design proposal | architect | `engineering:system-design`, `engineering:architecture` | Check boundaries, data flow, failure modes, simpler alternatives |
| `testing-strategy` | Design a test plan/strategy for a feature or area | qa-lead | `engineering:testing-strategy` | Risk-based pyramid: what to unit/integration/e2e test and why |
| `incident-response` | Triage, communicate, and post-mortem an incident | obs-chief, devops | `engineering:incident-response` | Severity → mitigate → root cause → blameless post-mortem in the incidents category |
| `debug` | Systematic root-cause investigation | obs-chief, support, sr-backend | `engineering:debug`, systematic-debugging skills | Reproduce → isolate → hypothesize → verify; never fix before understanding |
| `documentation` | Write/maintain docs, runbooks, changelogs | devrel | `engineering:documentation` | Audience-first structure; keep close to code; verify examples run |
| `standup-summary` | Compile activity into a standup format | scrum-master | `engineering:standup` | Yesterday / today / blockers from git log, issues, and discussions |
| `deploy-checklist` | Pre-deployment verification | devops | `engineering:deploy-checklist` | Verify CI green, migrations reviewed, rollback path, monitoring in place |
| `feature-development` | The client's own dev workflow (brainstorm → spec → plan → implement) | cto, product-chief, sr-backend | the project's own workflow/spec-driven skills, if any | Break work into spec → plan → tasks in the issue tracker |
| `ticket-authoring` | Draft or enrich a work item to a testable contract: numbered acceptance criteria (EARS / Given-When-Then), Definition of Done, explicit `[NEEDS CLARIFICATION]` markers for open questions | dispatcher, cto, product-chief | `write-ticket` (vendored in `skills/companion/`), or any spec-driven ticket skill | Issue body with context, evidence, numbered ACs, DoD; unresolved unknowns as explicit open questions — never confident-sounding guesses |
| `ticket-implementation` | Take an accepted work item end-to-end to a PR: spec → plan → **human plan approval** → TDD → review → PR | sr-backend | `implement-ticket` (vendored in `skills/companion/`), or any ticket-to-PR pipeline skill | Chain `feature-development` modes (spec → plan → implement) with `code-review`, gating implementation on explicit human approval of the plan |

## skills-map.json Format

Lives in the client project at `.claude/hive/skills-map.json`, generated by the `setup` skill (which scans the environment for installed skills) and hand-editable:

```json
{
  "capabilities": {
    "code-review": "/code-review",
    "security-review": "/security-review",
    "architecture-decision": "engineering:architecture",
    "incident-response": "engineering:incident-response",
    "testing-strategy": null,
    "ticket-authoring": "write-ticket",
    "ticket-implementation": "implement-ticket",
    "feature-development": {
      "brainstorm": "conductor-new-track",
      "spec": "conductor-new-track",
      "plan": "conductor-new-track",
      "implement": "conductor-implement",
      "review": "conductor-review",
      "status": "conductor-status",
      "revert": "conductor-revert",
      "default": "conductor-status"
    }
  }
}
```

- Value is the skill/command name as invocable in that environment (slash command, `plugin:skill`, or project skill name).
- `null` (or absent) = no provider; the agent uses the fallback guidance from the registry above.
- **Mode mapping (object form)**: when a provider is a *family* of skills (spec-driven workflow suites like Conductor ship separate skills for planning, implementing, reviewing…), the value may be an object mapping **modes** to skills. Agents that invoke a capability with a mode — e.g. `capability:feature-development (spec mode)` — resolve their mode key first, then `default`, then fall back as if unmapped. The string form stays valid and means "one skill handles every mode".

## Rules

1. **Agents never name concrete skills** — AGENT.md and SKILL-*.md files reference `capability:{name}` only.
2. **Resolution happens at run time** — the agent reads `skills-map.json` at the start of its cycle.
3. **Fallbacks must be usable** — every capability in the registry defines what to do when unmapped. An unmapped capability is degraded, never blocking.
4. **New capabilities are added here first** — if two agents need the same generic practice, register it as a capability instead of writing a hive skill.
5. **Unattended contexts use the contract, not the conversation** — some providers are interactive (clarify questions, approval gates). An agent running unattended (dispatcher, scheduled cycles) applies the provider's OUTPUT CONTRACT (structure, markers, gates recorded as open questions) without the interactive phases; interactive providers run fully only when a human is in the loop (e.g. `ticket-implementation` dispatched to sr-backend).
